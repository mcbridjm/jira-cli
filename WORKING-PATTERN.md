# IBM Jira + Copilot CLI Automation

This folder documents and hosts the pattern established for driving IBM Jira (`https://jsw.ibm.com`) directly from GitHub Copilot / CLI, using a Personal Access Token (PAT) instead of interactive OAuth/login, so an assistant can read/write Jira issues non-interactively on your behalf.

## Contents

- `jira-cli.sh` — the automation script (copied from
  `~/jira-cli.sh` in WSL). See `SCRIPT-README.md` (copied
  alongside it) for full action-by-action documentation.
- `.env` — contains your Jira PAT (`PAT=<token>`). **Never commit this file
  to source control.** Treat it like a password.

## The working pattern (how this session actually operates)

1. **You hold the PAT, not the assistant.** The token lives only in
   `.env` on disk. The assistant never asks you to paste it into chat and
   never echoes it back — every script call sources it silently
   (`source .env` inside the script, with `set -a`/`set +a` to scope the
   export) and `unset`s the in-memory copy as soon as the HTTP call
   completes.

2. **One script, multiple actions**, invoked like a CLI subcommand:
   ```bash
   ./jira-cli.sh <comment|description|transition|create|assign|mysprint> ...
   ```
   This avoids sprawling one-off scripts per Jira operation — every new
   capability (transition, create, assign, sprint reporting) was added as
   a new `case` branch in the same file rather than a new file, per your
   "function agnostic" naming request.

3. **Assistant proposes, you approve, then it executes.** For anything
   that changes visible Jira content (story descriptions, new stories,
   status transitions), the assistant drafts the exact text/command and
   asks for explicit approval (via a yes/no or multiple-choice question)
   before running it. Read-only actions (like `mysprint`) don't require
   approval since they can't modify anything.

4. **Real script files, not inline shell snippets.** Every Jira call is
   made by writing/editing a real `.sh` file and running it
   (`wsl bash /path/to/script.sh args...`), never via inline
   `bash -c '...$VAR...'` commands. This avoids a confirmed PowerShell/WSL
   quoting bug where variable expansions (`$PAT`, `$VAR`) get silently
   mangled or emptied when passed through nested `-c '...'` layers — this
   caused a false "401 Unauthorized" scare earlier in the session even
   though the PAT and auth were fine the whole time.

5. **CRLF hygiene.** Any file created via the Windows-side file-editing
   tools gets CRLF line endings, which breaks bash (`$'{\r'` syntax
   errors, `.env\r` "No such file" errors). Every script is run through
   `sed -i 's/\r$//' script.sh` immediately after creation/edit and before
   execution.

6. **Single-hop transitions, explicit multi-hop chaining.** Jira
   workflows often require multiple transitions to reach a target status
   (e.g. To Do → In Work → Resolved). The `transition` action deliberately
   performs only one hop per invocation and prints the available next
   hops if the target isn't directly reachable — the assistant confirms
   each hop with you rather than auto-chaining, since intermediate
   statuses can trigger their own notifications/side effects.

7. **Non-destructive create.** Jira validates issue creation atomically,
   so a `create` call that's missing a required field fails cleanly
   without leaving a partial issue behind — this let us skip Jira's
   `createmeta` endpoint entirely (it's blocked/disabled on this VA
   instance, returning a misleading 404) and just POST the standard
   fields (`project`, `issuetype`, `summary`, `description`, optional
   `assignee`).

## Quick reference: actions

| Action        | Example |
|---------------|---------|
| `comment`     | `./jira-cli.sh comment EAWM-7384 "Applied the fix."` |
| `description` | `./jira-cli.sh description EAWM-7384 "$(cat new-description.txt)"` |
| `transition`  | `./jira-cli.sh transition EAWM-7384 "Resolved"` |
| `create`      | `./jira-cli.sh create EAWM "Summary" "Description" --type Story --assignee adam.schaefer2@va.gov` |
| `create` (with epic/sprint) | `./jira-cli.sh create EAWM "Summary" "Description" --epic EAWM-8837 --sprint 52476 --assignee adam.schaefer2@va.gov` |
| `assign`      | `./jira-cli.sh assign EAWM-7385 adam.schaefer2@va.gov` |
| `mysprint`    | `./jira-cli.sh mysprint EAWM` (also shows each issue's Sprint id/name — use this to find a `--sprint` value) |
| `field`       | `./jira-cli.sh field sprint` (looks up custom field ids by name, e.g. Epic Link/Sprint) |

Run the script with no arguments (or `-h`) for the full built-in help text,
which is always kept in sync with the script itself (it's generated by
printing the script's own header comment block).

## Why this pattern (rationale)

- **Auditable:** every Jira write this session made is a single,
  reviewable `curl` call inside a version-controllable script — not an ad
  hoc API call buried in chat history.
- **Safe by default:** destructive/ambiguous actions (multi-hop
  transitions, bulk creates) require explicit flags or fail loudly with
  guidance rather than guessing.
- **Reusable across sessions:** because the pattern is "script + .env",
  any future Copilot CLI session (or teammate) can pick up the same
  script and .env convention without re-deriving the API quirks
  (Bearer-not-Basic auth, `/rest/api/2` not v3, blocked `createmeta`,
  username-not-accountId for assignee) documented here and in
  `SCRIPT-README.md`.
